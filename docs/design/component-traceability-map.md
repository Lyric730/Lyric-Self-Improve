# 云瀚小程序组件与设计稿对应表

版本：v0.1
参考设计稿：`docs/design/imagegen-references/07-component-ui-kit-board.png`
用途：后续前端实现时，一个组件一个组件按设计稿区域扣，不允许只做“黑橙大概像”。

## 1. 结论

我知道当前组件分别对应设计稿的哪些部分。后续实现不按页面感觉乱写，而是按下表逐项还原。

设计稿本身已经分成 8 个编号区域：

| 设计稿区域 | 位置 | 对应前端组件 | 当前状态 | 下一步要求 |
| --- | --- | --- | --- | --- |
| `01 按钮` | 左上 | `YhButton`、图标按钮、危险/成功按钮、临近到点提示按钮 | 已有骨架，不够像 | 先扣主按钮、次按钮、危险按钮、成功按钮、图标按钮 5 类状态 |
| `02 模式卡片` | 上中 | `ModeCard` | 已有骨架，不够像 | 按抢 5 / 抢 7 / 抢 10 三张竖向切角卡重做 |
| `03 底分/倍率选择` | 右上 | `PointOptionGrid`、`RiskFormula` | 未实现 | 做 50/100/200 和 x1/x2/x3/x5 选中态、未选态、禁用态 |
| `04 计分与比分控件` | 中左 | `ScoreBoard`、`ScoreStepper`、`ForwardTimer` | 未实现 | 做 LED 比分、头像位、到点时间、+/- 计分、时间状态条 |
| `05 奖励模块` | 中中 | `RandomRewardCard` | 未实现 | 做普通奖励、冲刺奖励、奖励揭晓状态 |
| `06 段位与结算` | 中右 | `RankBadge`、`StarTrack`、`SettlementDeltaCard` | 未实现 | 做段位徽章位、积分进度、+1/+2/-100/0 变化卡 |
| `07 排行榜与列表` | 下左 | `TopThreePodium`、`LeaderboardRow`、`LeaderboardTabs` | 未实现 | 做前三领奖台、总榜行、同段位榜、好友榜 |
| `08 提示与状态` | 下右 | `StatusNotice` | 未实现 | 做时间不足、可结算、临近到点、娱乐赛四类提示 |
| `视觉元素 / 材质参考 / 色彩规范` | 最底部 | `tokens.wxss`、纹理资产、边框装饰 | 部分 token 已有 | 把台呢、木纹、金属、斜切边框转成 token 和图片资产 |

## 2. Button 对应哪里

`YhButton` 对应设计稿 `01 按钮` 区域。

必须实现的按钮类型：

| 类型 | 设计稿位置 | 用途 | 视觉特征 |
| --- | --- | --- | --- |
| 主按钮 | `01 按钮 / 主要按钮` | 开始挑战、确认下一步 | 橙色金属切角、强亮面、按下态更深 |
| 次按钮 | `01 按钮 / 次要按钮` | 临近到点提示、返回、低优先级操作 | 暗金属底、橙色描边、弱亮面 |
| 危险按钮 | `01 按钮 / 对局结果按钮` 红色 | 不服、退出本场、作废 | 深红底、红色描边、不能像普通系统按钮 |
| 成功按钮 | `01 按钮 / 对局结果按钮` 绿色 | 服了确认、可结算确认 | 深绿底、绿色发光边 |
| 图标按钮 | `01 按钮 / 图标按钮` | 加、减、返回、规则、静音、分享 | 小尺寸金属方块，默认 / 按下 / 禁用三态 |

验收标准：

- 不能只是普通圆角按钮加渐变。
- 必须有切角、金属边、按下态、禁用态。
- 小程序端按钮文字必须居中，不能被微信默认 button 样式影响。

## 3. Card 对应哪里

这里的 Card 不是一个泛泛的卡片概念，而是几类不同业务组件。

| 组件 | 对应设计稿 | 长什么样 | 实现方式 |
| --- | --- | --- | --- |
| `ModeCard` | `02 模式卡片` | 竖向切角卡，抢 5 选中为橙色高亮，抢 7 暗金属，抢 10 锁定态 | WXML/WXSS 实现，锁图标用 asset 或 CSS |
| `PointOptionGrid` | `03 底分/倍率选择` | 小金属按钮组，选中项橙色发光，未选项暗底 | WXML/WXSS 实现 |
| `RandomRewardCard` | `05 奖励模块` | 宝箱 / 奖励牌视觉，普通奖励和冲刺奖励不同 | 背景与宝箱用图片资产，文字动态渲染 |
| `SettlementDeltaCard` | `06 段位与结算` | +1 星、+2 星、-100 积分、0 变化四类状态卡 | WXML/WXSS + 星星资产 |
| `StatusNotice` | `08 提示与状态` | 红/绿/橙/灰四种状态提示块，带状态图标 | WXML/WXSS + 图标 |
| `LeaderboardRow` | `07 排行榜与列表` | 紧凑榜单行，含排名、头像、昵称、段位、积分、变化 | WXML/WXSS 实现 |

验收标准：

- 不允许所有 Card 共用同一种圆角暗色卡。
- 不同业务卡必须分别对应设计稿区域：模式卡、奖励卡、状态卡、榜单卡不是一个东西。
- 动态数据必须用代码渲染，不能把整张卡切成图片。

## 4. 实现顺序

第一轮只扣基础组件：

1. `YhButton`：对应 `01 按钮`
2. `ModeCard`：对应 `02 模式卡片`
3. `PointOptionGrid` + `RiskFormula`：对应 `03 底分/倍率选择`
4. `RandomRewardCard`：对应 `05 奖励模块`

第二轮扣比赛核心：

1. `ScoreBoard`
2. `ScoreStepper`
3. `ForwardTimer`
4. `StatusNotice`

第三轮扣荣誉和榜单：

1. `RankBadge`
2. `StarTrack`
3. `SettlementDeltaCard`
4. `TopThreePodium`
5. `LeaderboardRow`

## 5. 还原边界

必须还原：

- 构图比例
- 切角结构
- 颜色角色
- 选中 / 未选 / 禁用 / 按下状态
- 字号层级
- 主要数字的仪表感
- 奖励和段位的仪式感

不逐像素硬抄：

- 图片里的示例头像
- 示例昵称
- 具体纹理噪点
- 无法动态维护的整卡截图

## 6. 每个组件完成时的验收问题

每扣完一个组件都问：

1. 它对应设计稿哪一个编号区域？
2. 选中、未选、禁用、按下状态是否齐？
3. 动态数据是否仍然是代码渲染？
4. 在微信开发者工具里看是否接近设计图，而不是只在文档里成立？
5. 是否会增加员工或玩家操作复杂度？

## 7. 美术资产接入边界

复杂美术资产不在组件里用 CSS 临时画。`RankBadge`、`StarTrack`、`RandomRewardCard`、`SettlementDeltaCard`、`TopThreePodium`、电视大屏装饰资产接入前，先按 `docs/design/ui-asset-map.md` 完成抠图、透明边、预览图和边缘检测。

组件验收时要同时确认两件事：

1. 动态文字、分数、昵称、状态仍然由代码渲染。
2. 徽章、宝箱、胜利横幅、确认章等复杂图形来自正式 PNG 资产。
