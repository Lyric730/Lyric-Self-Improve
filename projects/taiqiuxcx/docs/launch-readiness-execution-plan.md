# 云瀚台球小程序上线级执行计划

状态：v1.0
日期：2026-05-27
用途：把小程序从“演示 MVP / 产品原型”推进到“可上线标准”的阶段计划。之后每个阶段都按本文执行、验证、审查、归档。

## 1. 总原则

- 目标不再是演示完整流程，而是逐页打磨到可上线。
- 页面可见内容必须是正式上线内容；内部校验、PM 说明、演示状态、mock、模拟、调试、临时、占位说明不得外显。
- 后端、会员、房间状态未接入时，可以用占位数据支撑页面，但呈现方式必须像正式线上状态。
- 一次只推进一个阶段，避免把页面、组件、规则、后台一起改乱。
- 每个阶段必须有明确范围、验收标准、验证命令、审查记录。
- 代码实现必须服从 `AGENTS.md`、PRD、页面流程规格和设计系统文档。
- 员工端默认最少步骤、最少学习成本，不做复杂后台感。
- 重要结论写回文档，不只留在聊天窗口。

## 2. 阶段工作流

每个阶段固定按 6 步走：

1. **确认范围**：列出本阶段只改哪些页面 / 组件 / 文档。
2. **更新文档**：先补需求、页面设计、验收标准或任务记录。
3. **执行实现**：只改本阶段范围，避免顺手大改。
4. **运行验证**：至少跑 JS、JSON、资产边缘、微信开发者工具预览；涉及页面流时增加路由自动化检查。
5. **Codex 审查**：用代码审查姿态检查 bug、回归风险、缺少状态、缺少测试或实现偏离。
6. **归档结果**：把验证结果、审查结论、遗留问题写进 `docs/dev-log.md`；必要时新增 `docs/reviews/` 阶段审查文档。

## 3. 阶段审查规则

每个阶段收尾必须形成审查结论，格式固定：

- **Findings**：优先列问题，按 P0 / P1 / P2 / P3 排序。
- **Scope Check**：本阶段是否越界改动。
- **Requirement Check**：是否满足本阶段验收标准。
- **Verification Evidence**：列出实际跑过的命令和结果。
- **Decision**：通过 / 修复后通过 / 阻塞。

严重级别：

| 级别 | 含义 | 处理规则 |
| --- | --- | --- |
| P0 | 会导致页面不可用、构建失败、核心流程断掉 | 立即修复，不能进入下一阶段 |
| P1 | 会影响上线质量、规则正确性、用户误操作或数据风险 | 本阶段修复后再归档 |
| P2 | 体验瑕疵、边界状态不足、可维护性问题 | 记录并尽量本阶段修 |
| P3 | 小的文案、间距、命名、注释问题 | 可记录进后续 polish |

## 5. 上线级阶段拆分

### Phase 0：执行框架与文档基线

目标：把上线级工作流、审查规则、验证命令落到文档。

范围：

- `docs/launch-readiness-execution-plan.md`
- `AGENTS.md`
- `docs/dev-log.md`
- 必要的验证脚本

验收：

- 后续阶段有固定执行顺序。
- 阶段收尾有明确 Codex 审查格式。
- 验证命令可以复制执行。

### Phase 1：挑战首页上线级打磨

目标：挑战首页只做“进店后能否开始挑战”的判断和入口，不再像演示页。

范围：

- `miniprogram/pages/challenge-home/`
- `miniprogram/utils/ladder-data.js`
- 必要时补共享样式
- 相关文档记录

必须完成：

- 展示门店、球桌、开台到点时间。
- 展示用户当前段位和全部模式共用段位。
- 内部校验开始挑战前的 3 个必要条件：微信登录、店内 100 米定位、球桌开台有效。
- 不能把内部校验清单直接展示给顾客；顾客只看到排位可用 / 暂不可用和下一步操作。
- 按钮状态要跟内部校验联动：不满足则不能进入等待房间，并给出用户态提示。
- 不在首页展示底分、倍率、计分器、结算详情。
- 页面要保留游戏感，但信息密度不能拥挤。

验收：

- `canStartChallenge=true` 时可进入等待房间。
- 任一必要条件失败时，主按钮禁用或给出明确提示。
- 首屏只承担“开始挑战 / 查看数据入口”的职责。

### Phase 2：等待与接受挑战流程

目标：把“发起方等人、挑战方接受”做成稳定上线流程。

范围：

- `waiting-room`
- `accept-challenge`
- 房间状态 mock / 后续接口占位

必须完成：

- 等待页突出房间号、球桌、发起人、对手加入状态。
- 接受页只保留接受 / 拒绝，不提前暴露复杂积分参数。
- 退出和拒绝路径明确。
- 不能出现“模拟对手扫码”等演示按钮；后端未接入时也只能显示正式房间状态和刷新/取消等真实动作。

### Phase 3：玩法与风险积分选择

目标：把抢 5 / 抢 7 / 抢 10 预留、底分、倍率、随机奖励讲清楚。

范围：

- `mode-select`
- `points-select`
- `match-confirm`
- 模式配置数据

必须完成：

- 抢 5、抢 7 当前开放；抢 10 可显示预留或后台配置。
- 开局前突出展示底分 × 倍率和随机奖励机制。
- 所有底分、倍率、奖励范围必须可由老板后台配置。
- 玩法选择必须真实传递到后续页面，不能后续页面继续读取固定演示参数。
- 用户可见文案不能出现“本页只选”“后台模板”“服务器记录”等实现说明。

### Phase 4：比赛计分与时间规则

目标：比赛中只服务记分和最低有效时间判断。

范围：

- `match-scoring`
- `time-insufficient`

必须完成：

- 正向计时，从 00:00:01 开始累计。
- 双方都能加减盘数。
- 未达到最低有效时间不能结算，只能继续打或续时。
- 到开台结束时间只提醒续时，不负责和开台软件自动同步比赛时长。
- 不能出现“演示进入结算”等人为跳过规则的按钮。
- 计分页必须接收开局确认页传入的玩法、底分、倍率和风险积分。

### Phase 5：结算、服 / 不服、结果页

目标：结算仪式感和规则一致性到位。

范围：

- `settlement`
- `refusal`
- `match-result`

必须完成：

- 赢家加 `底分 × 倍率 + 随机奖励`。
- 输家扣 `底分 × 倍率`。
- 随机奖励统一一套标准，不区分胜方败方奖励档。
- 服则结算；不服后对方同意可退出本场不结算，或选择再战。
- 加星、加分、扣分有明显反馈。

### Phase 6：个人数据、排行榜、积分礼遇

目标：把留客与荣誉展示做完整。

范围：

- `my-data`
- `rankings`
- `points-perks`

必须完成：

- 个人端排行榜包含店内总榜、同段位排行、微信好友排行。
- 段位排行榜独立入口或标签。
- 积分礼遇只展示前台兑换规则，不做复杂商城。
- 开台赠送 30 分、新用户初始 300 分、兑换门槛 1000 分均可由老板配置。

### Phase 7：员工端最简工作流

目标：员工只做必须动作，减少上手成本。

范围：

- 员工端页面组
- 球桌开台时间设置
- 异常比赛查看

必须完成：

- 员工只需要设置球桌开台结束时间。
- 到点提醒续时，不要求员工手动同步比赛时间。
- 员工端避免复杂规则配置。

### Phase 8：老板配置端

目标：把所有可调参数集中给老板控制。

范围：

- 老板配置端页面组
- 模式配置
- 奖励配置
- 段位规则配置

必须完成：

- 底分、倍率、随机奖励范围、续时冲刺奖励、开台赠送分、新用户初始分、兑换门槛全部可配置。
- 抢 10 是否开放可配置。
- 全部游戏模式共用一个段位。

### Phase 9：电视大屏与上线检查

目标：完成店内大屏展示和微信上线前检查。

范围：

- 电视排行榜页
- 发布配置
- 包体、权限、隐私、体验版检查

必须完成：

- 大屏有店内总榜、赏金猎人榜。
- 预留门店活动 / Logo / 赞助信息接口。
- 小米电视浏览器可打开大屏页；如果不稳定再考虑盒子或 mini PC。
- 小程序隐私权限说明覆盖定位、用户信息等能力。

## 6. 当前执行顺序

当前从 Phase 0 开始。

Phase 0 完成后，立即进入 Phase 1：挑战首页上线级打磨。

每完成一个 Phase，必须更新：

- `docs/dev-log.md`
- 如有设计系统变化：`docs/design/yunhan-codable-design-system-spec.md`
- 如有页面流程变化：`docs/design/player-flow-page-spec.md`
- 如有规则变化：`docs/prd-taiqiu-ladder-mvp.md`
- 如有审查详情：`docs/reviews/phase-xx-*.md`
